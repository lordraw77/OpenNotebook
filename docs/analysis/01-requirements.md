# 01 — Product Requirements (Product Owner)

> Status: draft v0.2 — 2026-11-05. Open decisions are tracked in [05-roadmap-and-decisions.md](05-roadmap-and-decisions.md).

## 1. Vision

OpenNotebook is a **self-hosted, fully containerized** knowledge platform with **grounded RAG chat**. Users upload heterogeneous
sources (documents, source code, archives, images, web pages, notes), organize them in a **Project → Workspace → Notebook**
hierarchy, and query them through an LLM that answers **only** from the material in the selected scope, with **clickable
citations** that open the exact passage in the original source.

Key goals:

1. **Trustworthiness** — no answer without a source; explicitly say when the information is not available.
2. **Controlled scope** — retrieval is limited to the selected node and its descendants, and only to active sources.
3. **No models inside the stack** — every model call (LLM, embedding, rerank, vision, OCR) goes to an external provider, chosen per pipeline phase. The project ships application code and infrastructure only.
4. **Multi-user** — visibility per Project/Workspace/Notebook with inherited permissions.
5. **Packaged** — the whole stack ships as container images and starts with a single command.

## 2. Glossary

| Term | Definition |
|---|---|
| **Project** | Root categorization node (e.g. `wifi`). |
| **Workspace** | Area inside a project (e.g. `documentation`, `source`). |
| **Notebook** | Leaf container inside a workspace (e.g. `source/modules`). Holds sources and notes. |
| **Scope** | The node selected for a search: it includes itself and all descendants. |
| **Source** | An ingested unit: file, image, URL, manual note, or a file extracted from an archive. |
| **Chunk** | An indexed semantic block of text with provenance (page, bbox, offsets, heading path, lines). |
| **Citation** | A reference from an answer to one or more chunks, rendered as `[Source 1, p. 4]`. |
| **Phase** | A pipeline step that uses a model: embedding, rerank, chat, summary, vision, OCR, graph extraction. |

## 3. Functional requirements

### 3.1 Source Engine — Ingestion

| ID | Requirement |
|---|---|
| ING-01 | Upload **PDF, TXT, Markdown, DOCX** (extensible: PPTX, XLSX, HTML, ODT, EPUB). Implemented: also HTML, code, images, archives, web pages and, with the `converter` profile, PPTX, XLSX, ODF, legacy Office and RTF. |
| ING-02 | Upload **source code files**, with language detection and structure-aware chunking (functions, classes, modules). |
| ING-03 | **Compressed archives** (zip, tar, tar.gz, tar.xz, 7z): extracted recursively; every contained file becomes a child source that keeps its original path (`firmware.zip!/src/radio.c`). |
| ING-04 | **Images** (PNG, JPG, WEBP, TIFF, plus images contained in PDF/DOCX, plus scanned PDF pages): **OCR** of the text + **description** generated by an external vision model; both indexed. |
| ING-05 | **Web scraping**: URL input, clean text extraction (no navigation, footer or ads), stored snapshot, optional JavaScript rendering. Optional bounded crawl (depth N, same domain). |
| ING-06 | **Manual notes**: built-in Markdown editor for quick notes; a note is a source indexed like any other. |
| ING-07 | **Asynchronous** ingestion with per-source status: `queued → parsing → chunking → embedding → graph → summarizing → ready` / `failed` (readable error + retry). |
| ING-08 | **Deduplication** by content hash within a notebook. |
| ING-09 | **Re-indexing** of one source or a whole scope (e.g. after changing the embedding model). |
| ING-10 | When a source is added: automatic **summary** and **suggested questions**. |

### 3.2 Chunking and indexing

| ID | Requirement |
|---|---|
| IDX-01 | **Semantic / structural** chunking (sections, paragraphs, tables, functions) with configurable **overlap**. |
| IDX-02 | Every chunk keeps its **provenance**: source, page, bounding boxes (PDF), character offsets, heading path, lines (code). |
| IDX-03 | **Embeddings computed by an external provider** with a multilingual model (Italian and English content); the model is pinned per index. |
| IDX-04 | Storage in a **local vector database** with scope and active-state filters. |
| IDX-05 | **Lexical index** (BM25 / sparse) for hybrid search on proper names, codes and identifiers. |
| IDX-06 | **Knowledge graph**: entity and relation extraction (e.g. `Module A —uses→ Function B`, `Document X —describes→ Component Y`) linked to the originating chunks. |
| IDX-07 | **Wiki-style index**: generated pages per entity/topic with backlinks to sources and related concepts, navigable in the UI. |

### 3.3 Hierarchy and scope

| ID | Requirement |
|---|---|
| SCP-01 | Hierarchy **Project → Workspace → Notebook** with **free nesting** (decision D1): a project is always a root; workspaces nest under a project or another workspace; notebooks nest under a project, a workspace or another notebook (e.g. `wifi/source/modules/driver/radio`). Maximum depth `NODE_MAX_DEPTH` (default 16). Sources belong to a notebook. |
| SCP-02 | A search on node N includes all sources of N's descendants. Example: `wifi` → everything; `wifi/source` → all modules; `wifi/source/modules` → only that notebook. |
| SCP-03 | Every source has an **active/inactive switch**; inactive sources are excluded from search without being deleted. A switch on a node applies to all descendants. |
| SCP-04 | Moving sources/notebooks/workspaces between nodes **of the same project** without re-embedding (metadata update only). Moves across projects are not allowed, because each project may use a different embedding model. |

### 3.4 Grounded RAG chat

| ID | Requirement |
|---|---|
| CHT-01 | **Strict system prompt**: the LLM answers only from retrieved context; if the information is missing it says so. |
| CHT-02 | **Inline citations** on every claim: `[Source n, p. x]` / `[Source n, §section]` / `[Source n, lines a–b]`. |
| CHT-03 | Clicking a citation opens the source and **highlights the matching text** (PDF: region; text/code: lines/offsets). |
| CHT-04 | **Post-generation validation**: citations to chunks that do not exist or were not retrieved are removed/flagged. |
| CHT-05 | **Advanced research**: question decomposition, multi-step (multi-hop) retrieval, graph-based context expansion, a "deep research" mode producing a cited report. |
| CHT-06 | **Streaming** answers. |
| CHT-07 | Conversation history per scope; any answer can be **saved as a note**. |

### 3.5 Notes

| ID | Requirement |
|---|---|
| NOT-01 | Notes column: notes created manually or saved from chat (citations preserved). |
| NOT-02 | A note can be promoted to an indexed source with a toggle. |

### 3.6 UI pages

| Page | Content |
|---|---|
| **Workbench** | 3 columns: **left** tree Project/Workspace/Notebook/Source with switches; **center** chat with cited sources; **right** notes. Source viewer panel with highlighting. |
| **Settings** | Providers and models per phase; API key management; users/groups and permissions on project/workspace/notebook. |
| **Upload** | Multi-file / drag & drop upload, target notebook selection, URL input, preview of archive contents. |
| **RAG Status** | Queues and jobs, per-source status, errors, counters (sources, chunks, entities), embedding model per index, re-index actions, service health. |

### 3.7 Model providers

| ID | Requirement |
|---|---|
| PRV-01 | Supported providers: **Groq, OpenRouter, Google Gemini, Cloudflare Workers AI, Cerebras, Mistral, NVIDIA (NIM / build.nvidia.com), Hugging Face, Ollama**. |
| PRV-02 | Each phase (embedding, rerank, chat, summary, vision, OCR, graph extraction) is assigned independently to a provider + model, with an optional **fallback chain** (e.g. Cerebras → Groq → OpenRouter). |
| PRV-03 | **No model is shipped or executed inside the stack**: no model weights in images, no inference containers, no local ML libraries (no PyTorch/ONNX runtimes). Ollama is an external provider like the others. |
| PRV-07 | **Model selectability**: every phase has a global default chain (administrators) and an optional **per-project override** (project owners), including a different embedding model per project. In the Workbench every user can pick the chat model among the enabled chat models; the project's chain is the default and the fallback order. |
| PRV-08 | Provider model catalogs are synced from the provider APIs with detected capabilities (chat, vision, embedding, rerank, OCR); administrators enable models, override capabilities, register unlisted models and test each model. Retired models (HTTP 404/410 on test) are marked unavailable. |
| PRV-06 | Rerank is optional: external rerank model (NVIDIA, Cloudflare, Hugging Face), LLM-based rerank, or disabled (fusion score only). |
| PRV-04 | Provider credentials are entered in Settings or via environment variables, stored encrypted, never returned in clear. |
| PRV-05 | "Test connection" and model listing per provider in Settings; rate-limit (HTTP 429) handling with backoff and fallback. |

## 4. Non-functional requirements

| ID | Requirement | Initial target (to be confirmed) |
|---|---|---|
| NFR-01 | **Everything packaged**: every application and infrastructure component is a container image; one command starts the stack. Models are never packaged. | mandatory |
| NFR-02 | Time to first token, excluding provider latency beyond the first token (scope ≤ 100k chunks). | p95 < 3 s with a fast provider (Groq/Cerebras) |
| NFR-03 | Ingestion throughput (text PDF), excluding provider latency. | ≥ 20 pages/min per worker |
| NFR-04 | Scale | 10–50 users, ≤ 1M chunks per instance (v1) |
| NFR-05 | Isolation: a user must **never** receive chunks from unauthorized scopes, not even indirectly through the LLM. | mandatory |
| NFR-06 | UI languages: English (default), Italian. Multilingual content. | Implemented: runtime switch in the top bar (browser language by default), dates and numbers follow the language. |
| NFR-07 | Observability: OpenTelemetry, structured logs, Prometheus metrics. | |
| NFR-08 | Deployment: Docker Compose (v1), Kubernetes-ready (Helm chart later). | |
| NFR-09 | Slow providers (e.g. a CPU-only Ollama on the LAN) must not block the UI: per-phase timeouts, queueing, visible progress. | mandatory |
| NFR-11 | The stack requires network access to at least one provider; with no reachable provider, ingestion jobs wait in queue and chat reports the provider error. | mandatory |
| NFR-10 | All documentation, code comments, UI default strings and commit messages in **English**. | mandatory |
| NFR-12 | Only open-source dependencies with permissive licenses for the shipped product (no license keys). This is why the UI uses Angular Material instead of PrimeNG ≥ 22 (ADR-011). | mandatory |

## 5. Main user stories (with acceptance criteria)

**US-01 — Scoped search**
*As* a developer *I want* to ask "how is the radio channel configured?" on workspace `wifi/source` *so that* I get answers from code only.
- Given scope `wifi/source`, the answer cites only sources whose path is under `wifi/source`.
- Sources with the switch off never appear in citations.

**US-02 — Not found**
*As* a user *I want* the system to say "I could not find this information in the selected sources" when context is insufficient.
- On an out-of-domain question set, the hallucinated-answer rate is < 5% (automated eval).

**US-03 — Clickable citation**
- Every factual sentence of an answer has at least one citation.
- Clicking opens the source at the correct page, and the highlighted text contains the passage used.

**US-04 — Code archive**
*As* a user *I want* to upload `firmware.zip` and find each file as a navigable source.
- Binary files are skipped and reported; source files are indexed with their path; nested archives handled up to a configurable depth.
- Malicious archives (zip bombs, path traversal) are rejected with no impact on the system.

**US-05 — Image**
- An image containing text yields both OCR text and a description; searching for a word present in the image finds it.

**US-06 — Automatic summary**
- Within N seconds of indexing completion the source shows a summary + 3–5 suggested questions that start a chat when clicked.

**US-07 — Permissions**
*As* an admin *I want* to give a group read-only access to `wifi/documentation` but not to `wifi/source`.
- Group members do not see `source` in the tree, and a chat on project `wifi` never cites sources from `source`.

**US-08 — Model change**
*As* an admin *I want* to change the embedding model and re-index with no chat downtime.
- The old index stays live until re-indexing completes (atomic switch).

**US-09 — Provider fallback**
*As* an admin *I want* to configure Cerebras as primary chat provider with Groq as fallback.
- When the primary returns 429/5xx or times out, the request is retried on the fallback and the provider actually used is shown on the message.

**US-10 — One-command start**
*As* an operator *I want* `docker compose up -d` (or `make up`) on a clean host to start a working instance.
- After startup all health checks are green and a test PDF can be ingested and queried with one chat provider key and one embedding provider key (one provider such as Gemini or Mistral can cover both).

## 6. Out of scope for v1 (proposal)

- Audio/podcast generation, real-time collaborative note editing, synchronized connectors (Drive, Confluence, Git) — v2 candidates.
- Arbitrary node nesting beyond 3 levels (see D1).
- Running any model inside the stack (permanently out of scope, see PRV-03).
- Offline / air-gapped operation (every model is external).
